[2026-10-02] #005 httpx2 / openai 버전 충돌 — TypeError: process() takes no keyword arguments
────────────────────────────────────────────────────────────────
발생 위치  : test_agents.py 실행 → OpenAI API 첫 호출 시
증상       : TypeError: process() takes no keyword arguments
             트레이스백 경로: httpx → httpx2 내부 함수
원인       : langsmith 0.14.3이 httpx2 패키지를 설치.
             langchain-openai가 openai 3.x를 의존성으로 당겨옴.
             openai 3.x는 httpx2를 사용하도록 설계되었으나
             httpx2의 process() 함수 시그니처가 변경되어
             키워드 인자를 받지 않아 TypeError 발생.
해결 방법  : pip install "openai==1.84.0"
             → openai 1.x 계열로 고정 (httpx2 아닌 httpx 사용)
해결 이유  : openai 1.x는 표준 httpx를 사용하며 langsmith와도
             안정적으로 호환됨. openai 3.x는 httpx2 의존성을
             갖는데, httpx2는 아직 인터페이스가 안정화되지 않아
             버전 간 충돌 발생. langchain-openai의 요구사항과
             실제 사용 가능한 openai 버전 간의 격차를 pinning으로
             해소하는 것이 가장 빠르고 안전한 방법.
현재 상태  : 해결 완료 (openai==1.84.0 으로 고정)
재발 방지  : requirements.txt에 openai==1.84.0 명시
             주요 패키지 업그레이드 전 버전 호환성 확인 필요

[2026-10-02] #004 search/ 모듈 — Playwright 브라우저 바이너리 없음
────────────────────────────────────────────────────────────────
발생 위치  : search/job_scraper.py
증상       : Playwright로 채용사이트 크롤링 시도 시
             "Executable doesn't exist" 에러 발생 가능
원인       : pip install playwright 는 Python 패키지만 설치.
             실제 브라우저(Chromium) 바이너리는 별도 명령어로
             다운로드해야 함. 이를 누락한 경우 발생.
해결 방법  : playwright install chromium 실행
해결 이유  : Playwright는 패키지와 브라우저 바이너리를 분리해서
             관리함. chromium, firefox, webkit 중 필요한 것만
             선택 설치할 수 있도록 설계된 구조.
             Chromium만 설치하면 용량을 최소화하면서
             대부분의 한국 채용사이트 접근 가능.
             (chromium ≈ 300MB / 전체 브라우저 ≈ 1GB+)
현재 상태  : 해결 완료 (requirements.txt 주석에 명시)
재발 방지  : 프로젝트 최초 세팅 시 아래 순서 필수
             1) pip install -r requirements.txt
             2) playwright install chromium

[2026-10-02] #003 BGE-M3 다운로드 실패 — HuggingFace 디스크 용량 오탐
────────────────────────────────────────────────────────────────
발생 위치  : rag/embeddings.py → BAAI/bge-m3 모델 다운로드
증상       : "Not enough free disk space: 0.00 MB" 에러
             실제 C드라이브 여유: 8.1GB / 필요 용량: 2.27GB
원인       : huggingface_hub 라이브러리의 디스크 잔여 용량
             계산 버그. 실제 여유가 있음에도 0MB로 잘못 측정.
             (특정 버전에서 Windows 경로 처리 오류로 추정)
해결 방법  : BGE-M3 대신 OpenAI Embeddings API로 전환
             모델: text-embedding-3-small (1536차원)
해결 이유  : 아래 3가지 대안 중 OpenAI API가 가장 실용적이었음

  대안 1) HuggingFace 캐시 경로를 D드라이브로 변경
          → 근본 해결이지만 라이브러리 버그라 재발 가능성 있음

  대안 2) huggingface_hub 버전 다운그레이드
          → 다른 패키지 의존성 충돌 위험

  대안 3) OpenAI Embeddings API 사용 ← 채택
          → 로컬 다운로드 불필요, 이미 OpenAI 키 보유,
            text-embedding-3-small은 성능도 충분,
            USE_OPENAI_EMBEDDINGS=false 설정으로
            나중에 언제든 BGE-M3로 전환 가능하게 설계

변경 파일  : rag/embeddings.py — OpenAI/BGE 선택 구조로 재설계
             .env — USE_OPENAI_EMBEDDINGS=true 추가
트레이드오프:
  장점 - 로컬 저장 불필요, 즉시 실행, 항상 최신 모델
  단점 - API 호출 비용 (약 $0.02/1M 토큰, 실사용 시 미미한 수준)
         인터넷 연결 필요
나중에 BGE-M3 전환하려면:
  1) .env에서 USE_OPENAI_EMBEDDINGS=false 변경
  2) 기존 Chroma DB 삭제 (rm -rf chroma_db/)
  3) 프로필 재업로드 (벡터 차원이 달라서 재인덱싱 필요)

[2026-10-02] #002 Windows 콘솔 UnicodeEncodeError (cp949)
────────────────────────────────────────────────────────────────
발생 위치  : test_keys.py 실행 시 (PowerShell)
증상       : UnicodeEncodeError: 'cp949' codec can't encode
             character '✗' (✗) / '✓' (✓)
원인       : Windows 기본 콘솔 인코딩이 cp949 (EUC-KR 계열).
             UTF-8 전용 특수문자(✓ ✗ 등)는 cp949에 없어서
             print() 시 에러 발생.
             macOS/Linux는 기본 UTF-8이라 동일 코드가 문제없음.
해결 방법  : 두 가지 조치 동시 적용
             1) sys.stdout.reconfigure(encoding="utf-8")
                → Python이 콘솔에 UTF-8로 출력하도록 강제
             2) 특수문자 제거 → ASCII 대체 표현 사용
                ✓ → [OK] / ✗ → [FAIL] / - → [SKIP]
해결 이유  : 1번 조치만으로도 동작하지만, ASCII 치환도 함께
             적용한 이유는 다음과 같음:
             - Windows Terminal이나 구형 CMD에서는
               UTF-8 강제해도 폰트가 특수문자를 지원 안 할 수 있음
             - [OK]/[FAIL] 형식이 가독성도 더 좋고 범용성 높음
             - CI/CD 환경(GitHub Actions 등)에서도 안전하게 출력 가능
적용 범위  : 모든 테스트 스크립트 (test_*.py)
재발 방지  : 새 스크립트 작성 시 파일 상단 두 줄 고정
             import sys
             sys.stdout.reconfigure(encoding="utf-8")

             → 'sk-proj-xLT2' 같은 실제 키 앞부분이 나오면 정상

================================================================
1. 프로젝트 개요
================================================================

프로젝트명 : GoodJob
목적       : 채용공고를 분석하여 사용자 적합도를 평가하고,
             회사에 최적화된 이력서를 자동으로 생성하는 AI 서비스

핵심 사용자 시나리오
--------------------
Step 1. 사용자가 회사 이름 또는 회사 로고/공고 이미지를 입력
Step 2. 시스템이 자동으로 해당 회사의 채용공고를 검색 및 수집
Step 3. 사용자가 기존 이력서(PDF)를 업로드하거나 직접 경력을 입력
Step 4. AI 에이전트가 공고와 프로필을 비교하여 적합도 점수(0~100) 산출
Step 5. 적합도가 충분하면 해당 공고에 최적화된 이력서 자동 생성
Step 6. 사용자가 이력서를 다운로드하거나 수정 요청 가능

개발 목표
---------
- 포트폴리오용 AI 프로젝트로서 다양한 최신 기술 적용
- LangGraph 에이전트 / RAG / 프롬프트 엔지니어링 / sLLM 파인튜닝 포함
- 한국어 채용 시장에 특화된 모델 및 데이터 파이프라인 구성

3. 사용 기술 상세
================================================================

────────────────────────────────────────────────────────────────
3-1. LangGraph (에이전트 오케스트레이션)
────────────────────────────────────────────────────────────────
선택 이유
  - 단순 LLM 호출이 아닌 '여러 단계를 거치는 파이프라인' 구성에 적합
  - 상태(State)를 노드 간에 공유하므로 데이터 전달이 명확
  - 조건부 분기(적합도 낮으면 이력서 생성 건너뜀)와 루프를 쉽게 구현

장점
  - 그래프 구조로 전체 흐름을 시각적으로 파악 가능
  - 각 노드를 독립적으로 개발·테스트·교체 가능
  - LangSmith와 네이티브 통합으로 실행 추적 가능
  - Human-in-the-loop 구현이 용이 (이력서 수정 인터랙션)

단점
  - LangChain 생태계에 종속됨
  - 버전 업데이트가 잦아 API가 자주 바뀜
  - 간단한 작업에는 오버엔지니어링이 될 수 있음

예상 문제
  - langgraph 버전 호환성 문제 (0.2.x vs 0.3.x API 차이)
  - 노드 간 상태 타입 불일치 시 런타임 에러 발생
  - 그래프가 복잡해질수록 디버깅이 어려워짐
    → 해결: LangSmith 트레이싱 활성화 필수

────────────────────────────────────────────────────────────────
3-2. RAG (Retrieval Augmented Generation)
────────────────────────────────────────────────────────────────
선택 이유
  - 사용자 이력서 전체를 LLM에 매번 넣으면 토큰 비용 과다 발생
  - 채용공고와 관련 있는 경험만 선택적으로 추출해야 이력서 품질 향상
  - 사용자 데이터를 로컬에 안전하게 저장 가능

장점
  - 토큰 비용 절감 (전체 이력서 대신 관련 청크만 사용)
  - 사용자 경험이 축적될수록 검색 품질 향상
  - 다양한 이력서 포맷(PDF, 텍스트)을 통일된 벡터로 변환

단점
  - 청킹 전략에 따라 중요한 경험이 잘릴 수 있음
  - 임베딩 모델 로딩 시간 (BGE-M3 초기 구동 약 30초)
  - 벡터 유사도만으로는 맥락 파악에 한계

예상 문제
  - BGE-M3 모델 다운로드 실패 (약 2.4GB, 네트워크 이슈)
    → 해결: HuggingFace 캐시 디렉토리 확인 또는 미러 사용
  - PDF 파싱 오류 (스캔본, 이미지 기반 PDF)
    → 해결: OCR 폴백 (pytesseract 추가) 고려
  - Chroma DB 동시 쓰기 충돌
    → 해결: 단일 프로세스 쓰기 또는 Redis 락 사용

────────────────────────────────────────────────────────────────
3-3. BGE-M3 임베딩 + BGE Reranker (2단계 검색)
────────────────────────────────────────────────────────────────
선택 이유
  - BGE-M3: 한국어/영어 모두 최고 수준 임베딩 성능
  - Reranker: 벡터 검색의 정확도 한계를 Cross-encoder로 보완

장점
  - 한국어 채용공고와 이력서 모두 높은 품질로 처리
  - 2단계 검색으로 정확도와 속도 균형 확보
  - 완전 로컬 실행 (추가 API 비용 없음)

단점
  - 두 모델 모두 로컬 다운로드 필요 (BGE-M3 약 2.4GB, Reranker 약 1.1GB)
  - Reranker는 후보 수가 많을수록 느려짐 (O(n) 추론)
  - RAM 사용량 증가 (모델 2개 동시 로딩)

예상 문제
  - VRAM 부족으로 GPU 연산 불가 시 CPU 폴백 → 속도 저하
    → 해결: RERANKER_ENABLED=false 설정으로 비활성화 가능
  - RAG_TOP_K_INITIAL=20 으로 설정 시 Reranker 추론 20회 발생
    → 해결: 초기값 조정 가능 (.env)

────────────────────────────────────────────────────────────────
3-4. OpenAI API (Anthropic)
────────────────────────────────────────────────────────────────
선택 이유
  - 복잡한 분석(적합도 평가)과 긴 텍스트 생성(이력서)에 최적
  - Vision 기능으로 이미지 → 회사명 추출 가능
  - 200K 컨텍스트 창으로 긴 이력서도 처리 가능

장점
  - 현재 시점 최고 수준의 텍스트 생성 품질
  - API 하나로 텍스트/비전/스트리밍 모두 처리
  - 안정적인 JSON 구조화 출력

단점
  - 유료 API (토큰당 비용 발생)
  - 인터넷 연결 필수
  - 응답 속도가 로컬 모델보다 느릴 수 있음

예상 문제
  - API 키 만료 또는 한도 초과
    → 해결: settings.has_anthropic_key 체크 후 로컬로 폴백
  - Rate Limit 초과 (429 에러)
    → 해결: exponential backoff 재시도 로직 추가 필요
  - 프롬프트가 길어질수록 비용 급증
    → 해결: RAG로 컨텍스트를 최소화하는 것이 핵심

3-5. Ollama + Qwen2.5-7B (로컬 LLM)
────────────────────────────────────────────────────────────────
선택 이유
  - 단순한 파싱 작업에 OpenAI API를 쓰는 것은 비용 낭비
  - 8GB VRAM에서 7B 4bit 모델 실행 가능
  - 오프라인 환경에서도 기본 기능 동작 보장

장점
  - 추론 비용 무료
  - 데이터가 로컬에서만 처리됨 (개인정보 보호)
  - 파인튜닝 후 커스텀 모델 교체 용이

단점
  - Claude에 비해 품질 낮음 (7B vs 수백B)
  - Ollama 서버를 별도로 실행해야 함
  - 처음 모델 로딩 시 약 10~30초 소요

예상 문제
  - Ollama 서버 미실행 시 전체 로컬 처리 실패
    → 해결: LLMRouter가 자동으로 Claude로 폴백
  - 한국어 품질이 영어보다 낮을 수 있음
    → 해결: 파인튜닝으로 한국어 채용공고 특화 가능
  - 14B 모델을 CPU 오프로딩으로 실행 시 속도 매우 느림
    → 해결: 로컬 작업은 7B로 제한, 복잡한 작업은 Claude 사용

3-6. Playwright (웹 크롤링)
────────────────────────────────────────────────────────────────
선택 이유
  - 사람인, 잡코리아 등 JS 렌더링 기반 채용사이트 크롤링에 필수
  - BeautifulSoup은 정적 HTML만 파싱 가능, Playwright는 동적 사이트 지원

장점
  - JavaScript 렌더링 후 HTML 파싱 가능
  - 로그인이 필요한 페이지도 처리 가능
  - 비동기 처리로 다중 사이트 동시 크롤링 가능

단점
  - Chromium 설치 필요 (약 200MB)
  - 크롤링 차단(봇 감지)에 취약
  - 채용사이트 UI 변경 시 셀렉터 수정 필요

예상 문제
  - 크롤링 차단 (403, Cloudflare 등)
    → 해결: User-Agent 변경, 딜레이 추가, Tavily API로 대체
  - 채용사이트 HTML 구조 변경 시 파싱 실패
    → 해결: 정기적인 셀렉터 점검 및 업데이트
  - playwright install 미실행 시 브라우저 없음 에러
    → 해결: requirements.txt 설치 후 playwright install chromium 필수

3-7. Unsloth + LoRA (sLLM 파인튜닝)
────────────────────────────────────────────────────────────────
선택 이유
  - 일반 7B 모델을 한국어 채용공고 파싱에 특화시키기 위함
  - 이력서 문체 교정에 특화된 모델 필요
  - Unsloth: 동일 VRAM에서 2~5배 빠른 파인튜닝 속도

장점
  - Unsloth: 4bit 양자화로 8GB VRAM에서 7B 파인튜닝 가능
  - LoRA: 전체 가중치가 아닌 어댑터만 학습 → 빠르고 저장공간 적음
  - 파인튜닝 후 특정 태스크 품질이 Claude급으로 향상 가능

단점
  - 학습 데이터 수집 및 정제에 많은 시간 필요
  - 과적합(overfitting) 위험
  - Unsloth가 Linux/CUDA 환경에서만 완전 지원
    (Windows는 WSL2 또는 Colab 권장)

예상 문제
  - Windows 환경에서 Unsloth 설치 오류
    → 해결: WSL2에서 실행하거나 Google Colab 사용
  - VRAM 8GB에서 배치 크기 1로도 OOM 발생 가능
    → 해결: gradient_accumulation_steps 늘리고 batch_size=1 유지
  - 학습 데이터 부족 (100개 미만이면 과적합)
    → 해결: OpenAI API로 합성 데이터 생성 (data_collector.py)

────────────────────────────────────────────────────────────────
3-8. FastAPI + Streamlit
────────────────────────────────────────────────────────────────
선택 이유
  - FastAPI: Python 최고 성능 비동기 웹 프레임워크, 자동 API 문서화
  - Streamlit: Python만으로 웹 UI 구성, 빠른 프로토타이핑

장점
  - FastAPI: /docs 에서 자동 Swagger UI 제공
  - FastAPI: 비동기(async) 지원으로 LLM 호출 중 블로킹 없음
  - Streamlit: React/HTML 없이 Python으로만 UI 구성

단점
  - Streamlit: 상태 관리가 복잡, 페이지 리로드 시 상태 초기화
  - Streamlit: 커스텀 디자인에 한계 (나중에 Next.js 교체 고려)
  - FastAPI + Streamlit 2개 서버를 동시에 실행해야 함

예상 문제
  - Streamlit에서 LLM 스트리밍 응답 표시 시 지연
    → 해결: st.write_stream() 사용
  - FastAPI 비동기 코드에서 동기 LLM 호출 시 블로킹
    → 해결: asyncio.run_in_executor() 또는 async 클라이언트 사용

4-B. TIO(티오) 벤치마크 분석 및 GoodJob 추가 기능 후보

────────────────────────────────────────────────────────────────
TIO vs GoodJob 기능 비교
────────────────────────────────────────────────────────────────

기능                        TIO   GoodJob   비고
──────────────────────────────────────────────────────────────
채용공고 분석 (키워드 추출)   ✅    ✅        동등
이력서/자소서 자동 생성       ✅    ✅        동등
적합도 점수 (0~100%)         ❌    ✅        GoodJob 독자 강점
STAR 경험 구조화             ✅    ❌        TIO 핵심 기능 - 추가 필요
경험 재사용 라이브러리        ✅    ❌        추가 필요
면접 예상 질문 생성          ✅    ❌        추가 필요
자소서 문항별 작성 모드       ✅    ❌        추가 필요
실시간 첨삭(타이핑 중 AI)    ✅    ❌        Streamlit 한계로 보류

────────────────────────────────────────────────────────────────
[추가 후보 A] STAR 경험 구조화 (우선순위 1)
────────────────────────────────────────────────────────────────
개요
  사용자가 경험을 자유 텍스트로 입력하면 AI가
  Situation → Task → Action → Result 4단계로 자동 변환.
  구조화된 경험을 벡터 DB에 저장 → RAG 검색 품질 향상 부수효과.

예시
  입력: "FastAPI 서버 개발해서 성능 개선"
  출력:
    Situation : 기존 Django 서버가 동시 300건 요청에서 타임아웃 발생
    Task      : FastAPI 전환 및 비동기 처리 구조 설계 담당
